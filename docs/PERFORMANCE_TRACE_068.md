# 0.68: Record trace / Stop + Save

The vector front panel and Settings/Devices both expose command125:
**Record trace -> Stop + Save trace**. It records host performance telemetry
through Play/Stop and Legacy/SSM switching, avoiding repeated manual captures.
It is off at startup and is not persisted as enabled.

## User workflow

1. Boot the bank and click Record trace on the vector panel, below the status.
2. Leave about5s idle, press the firmware Play button and reproduce the load.
3. Switch Legacy, then back to the same SSM96k/192k setting; keep it running
   for another5–10s. Continue normal playing if that is part of the symptom.
4. Click Stop + Save trace and choose a location for the `.jsonl` file.

The stopped buffer is retained if the save dialog is cancelled or writing
fails. The button becomes Save trace for retry. A successful save permits a
fresh recording. Closing the application with unsaved data offers save,
discard or cancel. Closing only Settings hides it and does not stop recording.
The separate Capture MIDI/Save trace controls remain MIDI-message capture.

## Data and timing

The UI takes compact snapshots at most every250ms. While recording, a separate
WindowsThreadCapture instance enumerates process threads once per second using
GetThreadTimes. Its series does not disturb manual capture's previous sample.
Thread IDs plus creation times protect against reuse; a new thread initially
has busy=-1. Busy is a fraction of one logical CPU, not Task Manager's process
percentage. The trace includes the logical processor count for interpretation.

Samples contain actual mode, machine/audio generation, emulated tick, speed,
owner CPU busy, quantum durations, pacing debt/rebases, audio queue and
cumulative/interval drop/missing counts, DSP queue/load/wait times, solver work
and recovery counters, DC/clipping, calibration revision, MIDI UART counts,
CPU PCs/HALT/WAIT, DMA/DRAM counters, drive state,24CVs and knownness, LCD/error.
Paused/offline pacing lateness is reported as0 rather than attributing paused
wall time to a running machine. Boot resets host measurement baselines.

Panel contact down/up, host buttons, requested chip changes and output-device
changes are timestamped. The applied mode and generation appear in subsequent
samples. Requested event timestamps are UI dispatch times, not exact firmware
acceptance ticks. Rapid changes between samples can skip an intermediate mode;
the generation and request events make that visible. Solver counters must not
be subtracted across audio generations. A boot has its own machine generation.

Calibration is recorded at the next sample after a change; rapid slider edits
coalesce. A final full profile and processor-count event are appended at stop,
so they remain present even if a long recording dropped the initial rows.
WASAPI diagnostics, WinMM counts and per-thread observations are1Hz events.
The full text Machine::report is never generated by this recorder, and it does
not freeze/change the serial report selection. No instruction history, audio
payload, media content or ROM/disk paths are collected.

## Ownership and bounds

Additional CPU/CV metrics are read by the existing machine owner only after
an explicit TraceMetrics command. Off snapshots have trace.enabled=false;
there is no new thread enumeration, recorder sampling, JSON formatting or
periodic file I/O when disabled. Existing baseline counters keep their existing
behavior. Machine/audio generation integers are cheap lifecycle markers.

Formatting and a bounded deque are UI-owned, outside the machine/DSP callbacks.
There is no new background sampler, no solver instrumentation and no audio
queue policy, firmware execution, filter transfer or pacing change. Output is
written only after recording stops. Sampling is skipped across UI stalls;
there is no catch-up loop. Recording has measurement overhead and is not a
proof that a target CPU symptom is fixed.

The buffer retains at most4096 rows and4MiB of row data. It discards the oldest
rows when either limit is hit, and the exported header declares the count.
An individual event detail is limited to8192 bytes, with truncation flagged.
Header memory, deque/string overhead and temporary export copy are additional
to the4MiB row-data bound. Nonfinite numeric telemetry becomes JSON null;
arbitrary LCD/control characters are escaped. Relative ms values are observed
wall times and ticks are the most recently published worker state.

## Validation

- performance_trace_tests: off/pending guards; timestamps; mode generations;
  counter reset; escaping/nulls; stop freeze; burst/long recording bounds;
  explicit truncation; new recording reset.
- performance_trace_session_tests: same seeded synthetic Z80 execution with
  trace off/on yields identical complete digital reports; enabling/disabling
  does not advance CPU; model/boot generations track actual lifetime changes.
- vector_panel_tests: trace button target is unique, within the layout and
  does not overlap existing host buttons or faders; original contacts remain.
- Existing panel session, serial publication, pacing and command-wake tests
  pass. An independent Python parser accepts the synthetic exported JSONL.
- Win64 O3/LTO/NDEBUG/DIAG0/Unicode cross-build with Wall/Wextra/Werror passes.
  Windows GUI execution, save/cancel dialogs and measured target overhead
  have not been run in this environment. SVG export is a design preview.

The0.67 private branch plus the filter restart audit18c0fab is the parent.
This provides the requested diagnostic workflow, not a speculative Play fix.
